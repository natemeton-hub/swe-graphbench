Abstract

Local coding agents built on Gemma 4 navigate repositories through a 32k-token window and a bounded tool budget, so the code-intelligence tools the competition harness exposes are the only repository-level navigation an agent has. We audit the graphs and embeddings behind those tools and find them structurally weaker than their interface suggests: graphs exist for only 68 of the 129 public tasks; in every graph 100% of calls edges are reciprocal, so caller/callee direction is lost; a median 68% of nodes have no edge; a median 9% of nodes are library code against 64% test code; 99.7% of async def definitions are missing and nested functions are hoisted into colliding identifiers; and no node carries a file path or line number. We release SWE-GraphBench: (1) the audit as reproducible scripts; (2) a ~300-line pure-standard-library graph builder that emits the competition schema with directed call edges, async and nested definitions, location attributes and contains/imports/inherits edges, fast enough to run inside the air-gapped sandbox; (3) corrected graphs for all 127 task commits, including the 59 rich and requests commits that have no released graph, plus documented Qwen3 embeddings that can be queried with issue text; (4) a benchmark of 121 tasks with patch-derived gold symbols, LLM-free baselines, paired bootstrap statistics and an explicit coverage ceiling; and (5) the same graphs and gold symbols for all 500 SWE-bench Verified tasks across 12 further repositories. Moving from the graph as shipped to the rebuilt graph raises the best lexical retriever's Hit@5 from 0.34 to 0.49; documented embeddings raise MRR from 0.28 to 0.40; and on SWE-bench Verified the identical pipeline reaches Hit@5 0.54. Everything is Apache-2.0.

1. Introduction

The Gemma 4 Developer Agent competition asks for an agent that fixes real GitHub issues offline on a single accelerator, with a 32,768-token context, a per-task tool-call budget and a 4 GiB sandbox. Under these constraints the first and most expensive sub-problem is localization: finding the few functions an issue is about before the context fills with irrelevant file reads. Agentless and graph-guided agents such as LocAgent report that most end-to-end failures on SWE-bench are localization failures and that a code graph is the most effective structure for narrowing a repository to a few candidates.

The organizers released such a structure: per task commit, a NetworkX node-link JSON graph of symbols with calls edges and a 256-dimensional embedding per symbol, exposed through three sandboxed tools. The artifacts themselves have not been examined, and because the hidden test set uses private repositories, an agent cannot bring a precomputed graph: whatever graph exists at evaluation time is the organizers' or one the agent builds inside the sandbox.

This paper treats the released artifacts as an object of study and then fixes what the audit finds. Our contributions are:

- An audit (Section 3) of all 68 released graphs and 127 embedding archives, every statistic produced by a script.
- A builder (Section 4.2) that emits the same JSON schema from source with nothing but Python's ast module: every definition including async and nested ones, directed call edges annotated with their resolution rule, containment, import and inheritance edges, and file and line attributes. It runs in about 20 s on FastAPI, so an agent can run it as a skill script on an unseen repository.
- Corrected graphs and documented embeddings for all 127 (repository, commit) pairs, including the 59 rich and requests commits for which no graph exists, released as a Kaggle dataset.
- A benchmark (Section 4) of 121 tasks with patch-derived gold symbols and a protocol that reports the coverage ceiling next to every retrieval number, so "the graph cannot represent the answer" is never confused with "the retriever missed it".
- Generalization (Section 5.4): graphs, gold symbols and results for all 500 SWE-bench Verified tasks.

Everything is deterministic and runs on a laptop CPU with no language model in the loop: the question is what the graph supports, and an LLM would confound graph quality with prompt quality.

2. Related work

SWE-bench (Jimenez et al., 2024) and its Lite and Verified subsets define the issue-to-patch task we inherit; SWE-Gym (Pan et al., 2025) and SWE-smith (Yang et al., 2025) scale training data for it. We change the label from "tests pass" to "the symbols the reference patch edits", scoring retrieval rather than resolution.

Agentless (Xia et al., 2024) measures how often hierarchical localization contains the ground-truth file and elements; LocAgent (Chen et al., 2025) introduces Loc-Bench with function-level Acc@k over a self-built code graph; SweRank (Reddy et al., 2026) shows trained retrieve-and-rerank can match agents; CoSIL (Jiang et al., 2025), OrcaLoca (Yu et al., 2025), KGCompass (Yang et al., 2025), GraphLocator (Liu et al., 2026) and RepoNavigator (Zhang et al., 2025) localize over graphs they construct, and ARISE (Seddik et al., 2026) packages such a graph as an agent toolset. GREPO (Wang et al., 2026) is the closest academic benchmark: class- and function-level localization over repository graphs with Hit@K, built for GNN training. None study an externally supplied, fixed graph or report its coverage ceiling, which is the situation a competition agent faces. RepoGraph (Ouyang et al., 2025), CodexGraph (Liu et al., 2025), CodeRAG (Li et al., 2025), GraphCoder (Liu et al., 2024), RepoCoder (Zhang et al., 2023) and CodePlan (Bairi et al., 2023) use dependency structure for generation; our PageRank baseline is their LLM-free analogue.

Concurrent competition entries. Two public paper-track repositories independently compare BM25, embedding and one-hop graph retrieval on the released artifacts with patch-derived gold (aghasalim, 2026; satiricalguru, 2026); both note that search_similar_code only accepts symbol names. Our audit confirms and extends their observations; what we add is the corrected resource: a sandbox-runnable builder, graphs and documented embeddings for every task, a frozen gold set with paired statistics, a released-versus-rebuilt comparison under identical conditions, and the extension to SWE-bench Verified.

3. The released artifacts: an audit

Setup. The public release contains tasks.jsonl (129 tasks: 67 fastapi/fastapi, 48 Textualize/rich, 13 psf/requests, 1 encode/httpx), 68 graph files and 127 embedding files keyed by <repo>_<sha>. We cloned the four repositories and verified that every base commit resolves; all numbers come from scripts 02 and 06 in the repository.

Availability. Graphs exist for the 67 FastAPI commits and the single httpx commit only. The 61 rich and requests tasks have embeddings but no graph, and because the harness enables the tools only when both files exist, agents on those tasks receive no code-intelligence tool.

Structure (Figure 1). Every graph has a single edge type, calls. In all 68 graphs, 100% of edge pairs are reciprocal: for every A calls B there is a B calls A, so get_code_neighbors cannot distinguish callers from callees. A median 68% of nodes are isolated (3% for httpx to 72%), a median 64% are test functions and only 9% belong to the library package. The highest-degree node in every FastAPI graph is the FastAPI class (degree 123), suggesting calls resolved by name matching rather than scope.

(Figure 1. Four structural measures of the 68 released graphs, one dot per graph. See the media gallery.)

Node attributes and identifiers. Nodes carry only id, name and text: no file path, line number, kind or parent. Comparing node sets against an ast walk of the same commit (Section 4.2) shows three systematic omissions: (i) async def is not a node: 69,845 of 70,070 async definitions across the 68 commits (99.7%) are absent, including FastAPI's solve_dependencies, serialize_response and the request-handler closure app; (ii) nested synchronous functions are hoisted to their enclosing class or module (8,034 released ids), so distinct closures share one identifier and 2,095 released ids are ambiguous; (iii) 2,289 released ids (0.9%) have no counterpart at all. Overall 25.0% of the 341,563 definitions present at those commits have no released node.

Embeddings. Each archive maps symbol name to a 256-d float32 vector; keys match the node ids exactly. Vectors are unnormalized and deterministic in the node text: 14.6% of rows in a FastAPI archive are exact duplicates, all with identical source. The model is undocumented, and because the sandbox has no encoder, search_similar_code must be queried with a symbol name, never with issue text.

Coverage of what fixes edit. On the 65 tasks with a graph and at least one gold symbol (Section 4.1), 85.3% of gold symbols exist as nodes and 78.8% also have an edge; 45 of 65 tasks have every gold symbol represented and 4 have none. Missing gold symbols are almost all async or nested definitions.

4. SWE-GraphBench

4.1 Gold symbols

For every hunk of the reference patch in a modified Python file we take the old-file lines it removes (for pure insertions, the preceding context line), read the file at base_commit, and record the innermost enclosing def or class by ast line spans including decorators. Symbol ids use the released convention: dotted path from the repository root with a leading src/ or docs_src/ dropped, full nesting kept. Added files, non-Python files and module-level edits are kept as separate fields rather than dropped. 121 of 129 tasks have at least one gold symbol (median 1, max 141). Gold symbols are necessary, not sufficient, locations, but they are the deterministic proxy used by Agentless, LocAgent and GREPO.

4.2 Builder

swegraphbench/build_graph.py parses every .py file with ast and emits a node per module, class, function and async function with its full qualified name, kind, file, lineno, end_lineno, is_async, parent, first docstring line and source text. Edges are contains, imports (relative imports resolved), inherits and directed calls. Call targets are resolved in a fixed order and each edge records the rule that fired: self (through the class and its resolved bases), scope (module definitions and import bindings, including class instantiation), enclosing (nested function calling an outer-scope sibling), suffix2 (obj.method unique in the repository) and suffix1 (bare name unique in the repository). Unresolvable calls, mostly to the standard library and third-party packages, are counted but never guessed, so consumers can filter edges by confidence. The harness tools load the file unchanged.

The builder has no dependency outside the standard library, is about 300 lines, and processes a FastAPI commit (1,120 files, 6,400 nodes) in roughly 20 s on one laptop core. A unit test on a synthetic package checks every resolution rule and that no reciprocal pair is produced. Against the released graphs, 53,793 of the 81,967 released undirected call pairs (65.6%) are also found by the resolver; it emits 142,657 directed call edges over the same 68 commits, at most 1.4% of them reciprocal.

4.3 Baselines and metrics

All baselines take the problem statement and the graph (plus embeddings when available) and return a ranked list of node ids:

- BM25 over identifier-split tokens of the source text.
- Symbol seed: identifiers mentioned in the issue resolved to nodes with the harness's four-tier rule (exact, suffix, case-insensitive, substring), ranked by weighted mention count: the strongest query the released search_similar_code can express.
- Embedding expansion: the mean released vector of the top seeds, expanded by cosine similarity.
- Personalized PageRank from the top-10 BM25 seeds over calls edges.
- Dense (Section 5.3): cosine similarity between the issue text and node embeddings from a documented open model.
- Hybrid: reciprocal-rank fusion of the lists above.

Each condition may drop test nodes from the candidate set, a filter any library-fixing agent can apply for free. We report Recall@k and Hit@k for k in {1, 5, 10, 20} and MRR, averaged over tasks with 95% bootstrap confidence intervals (2,000 resamples) and paired sign tests, always alongside the coverage ceiling: the Recall a perfect ranking could reach given which gold symbols are nodes.

5.1 Released versus rebuilt graphs

Filtering tests is the single largest cheap win. Removing test nodes from the candidate set raises BM25 Hit@5 on the released graph from 0.292 to 0.415 (paired 95% CI +0.03 to +0.22, sign test p = 0.02) and Recall@10 from 0.253 to 0.321 (p = 0.006).

The rebuilt graph helps on top of that, modestly. With tests filtered in both, the rebuilt graph lifts the hybrid retriever from 0.431 to 0.492 Hit@5 and 0.350 to 0.403 Recall@10 (paired CI âˆ’0.01 to +0.12, 15 wins / 5 losses, p = 0.04) and PageRank MRR from 0.201 to 0.266; at 65 tasks not every metric's gain is individually significant. The gain has two sources the audit predicted: the coverage ceiling rises from 0.854 to 1.0, and scope-resolved call edges give PageRank a cleaner neighbourhood. End to end, from the graph as shipped to the rebuilt filtered graph, the hybrid gains +0.154 Hit@5 (p = 0.02) and +0.134 Recall@10 (p < 0.001).

Edge direction does not help seed expansion. Propagating from BM25 seeds toward callees only is worse than undirected propagation (PageRank Hit@5 0.369 vs 0.431), toward callers only worse still (0.338). Direction still matters for tool semantics: get_code_neighbors can finally answer "who calls this".

The released embeddings add nothing measurable. Because its query must itself be a resolved symbol, embedding expansion returns nothing on the 26 of 65 tasks whose issue names no resolvable symbol, matches symbol seeding's top-5 on 45 tasks, and adding the vectors to the rebuilt graph leaves every metric unchanged or marginally lower.

5.2 Tasks the release left uncovered

On the 56 rich and requests tasks with gold symbols and no released graph, the rebuilt graph with tests filtered reaches Hit@5 0.500, Recall@10 0.478 and MRR 0.358 with the lexical hybrid (Figure 3), on par with the FastAPI tasks. Under the released artifacts an agent on these tasks has no graph tool at all.

(Figure 3. Localization on the 56 rich and requests tasks using only the rebuilt graph. See the media gallery.)

5.3 Documented embeddings that accept issue text

We embedded every non-test node of the rebuilt graphs (7,079 unique texts across the 120 benchmark commits) with Qwen3-Embedding-0.6B (Apache-2.0, 1,024-d) on a Kaggle T4 in 100 s, and the issue text as the query. On all 121 tasks, dense retrieval alone reaches Hit@1 0.256, Hit@5 0.521 and MRR 0.391 against 0.124 / 0.438 / 0.251 for BM25 and 0.157 / 0.479 / 0.284 for the lexical hybrid (BM25 + PageRank). Fusing BM25 with dense gives 0.281 / 0.529 / 0.396: against the lexical hybrid that is +0.124 Hit@1 (p = 0.004), +0.083 Recall@10 (p = 0.005), +0.158 Recall@20 and +0.113 MRR (both p < 0.001, paired). A second model, bge-code-v1, scored far below BM25 under the default sentence-transformers configuration (Hit@5 0.058) and is reported as a negative result; both runs are in the public notebook. The Qwen3 archives are released in the competition's key-to-vector layout so they can replace the undocumented ones.

5.4 Generalization: SWE-bench Verified

To test that nothing is specific to the competition repositories, we ran the unchanged pipeline on all 500 SWE-bench Verified tasks (12 repositories, 499 commits; gold symbols for 484). Building the 499 graphs took 8.4 CPU-hours on a laptop (median 44 s, maximum 3 min for sympy; django graphs have a median 37,284 nodes). With tests filtered, the lexical hybrid reaches Hit@5 0.537, Recall@10 0.524 and MRR 0.378 over 484 tasks, with per-repository Hit@5 from 0.39 (sphinx) to 0.72 (scikit-learn) among repositories with at least 20 tasks (Figure 4), matching the competition repositories. The graphs and gold symbols are released as SWE-GraphBench-Verified.

(Figure 4. Hybrid Hit@5 per SWE-bench Verified repository (tests filtered); repositories with fewer than 8 tasks are pooled. See the media gallery.)

6. Limitations

Static resolution misses dynamic dispatch, rebinding decorators and calls through container attributes; the resolver reports these as unresolved rather than guessing. Gold symbols come from one reference patch; equally valid fixes can live elsewhere. On rebuilt graphs the coverage ceiling is 1.0 by construction, so Verified numbers measure retrieval only. We do not report an end-to-end resolution rate; the leaderboard measures that, and our claim is about the graph layer beneath it. Dense retrieval needs an encoder the sandbox lacks, so inside the competition it applies to precomputed graphs only.

7. Conclusion

The code graph an agent is handed is not neutral infrastructure. For the Gemma 4 Developer Agent release it is undirected, mostly tests, missing every async function, and absent for half the tasks. A builder small enough to run inside the sandbox removes all four defects, documented embeddings make the graph searchable by issue text, and the same pipeline transfers unchanged to SWE-bench Verified. SWE-GraphBench measures all of this with no language model in the loop: a drop-in improvement for competition agents and a reusable protocol for auditing any precomputed code graph before building on it.
